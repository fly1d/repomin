# 当前发布版真实案例复跑包

本包用**已经发布的 ReproMin dev14 wheel**，重新运行一个公开的 tsdown
CSS modules 故障案例。它包含完整输入、准备过程的差异、来源与文件哈希、运行脚本和一份结果。
仓库不包含 wheel 二进制文件，需显式下载已有发布产物，再由脚本检查哈希。

第一次维护者侧运行得到：**14 文件 / 32,788 字节 → 8 文件 / 31,342 字节**，
再用三份新副本复跑，**3/3 命中目标故障**。减少了 6 个文件、1,446 字节，
字节减少约 4.41%；锁文件占了大部分体积。这是一条流程的可行性证据，尚不能证明外部用户觉得好用。

## 如何运行

需要 macOS 或 Linux、PATH 中的 **Node v24.19.0 或 v26.5.0** 与 npm，以及带有
venv/ensurepip 的 Python 3.9+。实际验证的 macOS arm64 组合为 Python 3.9.6 /
Node 24.19.0，以及 Python 3.13.9 / Node 26.5.0，npm 均为 12.0.1。Linux 和
其他组合仍未验证；脚本会拒绝其他 Node 版本。

在仓库根目录，先下载已有发布版 wheel：

```sh
curl --http1.1 --fail --location --retry 2 --connect-timeout 15 --max-time 120 \
  https://github.com/fly1d/repomin/releases/download/v0.1.0.dev14/repomin-0.1.0.dev14-py3-none-any.whl \
  --output reproductions/tsdown-979/repomin-0.1.0.dev14-py3-none-any.whl
```

如果网络阻止该命令，可从 [dev14 发布页](https://github.com/fly1d/repomin/releases/tag/v0.1.0.dev14)
下载同名 wheel，放到 `reproductions/tsdown-979/`；预检会检查哈希。

然后检查环境、执行完整流程：

```sh
python3 reproductions/tsdown-979/run.py --check
python3 reproductions/tsdown-979/run.py ../tsdown-dev14-run
```

第一条只检查本地环境、案例文件与 wheel 哈希，不创建工作目录，不安装或下载依赖。
应显示 `"status": "ready"`；它尚未验证网络和构建。第二条才执行完整流程，
成功时显示 `"status": "passed"` 和结果摘要路径。

目标目录必须不存在，父目录须已存在。预检失败直接在终端提示，不创建工作目录；
执行开始后的失败记录会保留，重试时换一个新目录。
有空格的路径要加引号。首次准备需要网络；pnpm、Python 环境、依赖缓存都放在新目录里。
候选缩减和复跑的安装使用独立缓存及 `--offline --frozen-lockfile`。
**代码仍在本机执行，离线安装不等于安全沙箱。** 运行前应阅读脚本和案例代码。

第一次完整运行约两分钟，网络和机器配置会影响耗时。缩减预算为 300 秒、80 次尝试，
其他阶段另有限时。最终应显示 `status: passed`；非零退出表示本次没有通过。

脚本会检查：

1. 原始输入确实满足目标故障条件。
2. 缩减得到更少文件，且报告与产物的指纹一致。
3. 三次新副本复跑成功，不用 ReproMin 结果缓存。
4. 去掉目标 CSS 声明时应得到零次匹配；只保留一个导出时应明确被可用性检查拒绝。
   安装或构建出错不能当成负对照通过。
5. 原输入没有被修改，负对照也没有改动正式产物。

成功后查看新目录中的 `validation-summary.md` 和 `reduced/`。
`run-record.json`、完整报告及 `private-logs/` 是**私密排查材料**，可能含本机路径或命令输出，
不要作为常规反馈直接公开。可分享的技术结果为经过字段筛选的 `validation-summary.md`，分享前也应查看内容。
随包的 `reference-result/` 仅保留选定字段、文件哈希、8 文件结果和可分享摘要。
每次新运行会产生自己的完整报告；候选顺序、尝试数、最终留下的 CSS 文件对可能不同。

## 这份材料能证明什么

这是**从固定公开源码重新准备的当前版本验证**。旧 dev9 实验的原始 14 文件准备目录没有找回，
不能说本包恢复了那个历史快照。准备过程明确加入公开锁文件和判定脚本，并把原来的日志包装入口
改为四个 CSS 对象直接导出，差异在 `prepared-input.patch`。初始输入没有拿缩减结果来充数。

判定脚本会清除旧产物、构建、导入新模块，要求至少两个对象导出，再检查重复的
`cursor: pointer`、专用标记及退出码 23。它验证有限的故障与可用性条件，不能证明根因完全相同、
代码整体正确或生产可用。

当前实际 pnpm 为公开清单指定的 **11.8.0**；历史文档记载的 11.19.0 没有被当成此次运行环境。
完整固定提交、哈希、版本和许可见 [英文说明](README.md) 与 `provenance.json`。

## 如果卡住

| 提示或阶段 | 处理方式 |
| --- | --- |
| 缺运行时、ensurepip 或 Node 版本不同 | 使用已有的匹配环境，再执行 `--check`；该检查不创建工作目录。 |
| 目录已存在或父目录不存在 | 换一个父目录已存在的新路径，保留旧记录。 |
| `install-pnpm` / `warm-dependencies` | 本地查看该阶段私密日志和公开依赖源连接，保持锁文件与判定条件。 |
| `doctor` / 缩减 / replay | 本地查看 `run-record.json` 的停止阶段及对应日志，反馈简短脱敏错误。 |
